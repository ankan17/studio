## Decisions and findings

Choices made with the user before building (Nov 11 to 12): export history lives in `<project>/exports.json`, not in `project.json`, so schema v1 is unchanged; the destination comes from a native save dialog in main, with a versioned suggested name (`<project> v<n>.mp4`); export runs at the project's own frame rate only (an fps picker was considered and dropped, because `convertProjectFps` rounds each clip start and length separately and would need a fix first); the `@remotion/renderer` fallback at concurrency 1 is not built, since spike 3 passed.

- **Flow:** the renderer says only which project and which size (`exports:start`, `{projectId, height}`). Main reads the project from disk (so the editor flushes its autosave first), checks that every original the timeline plays exists, asks for the destination, refuses anything inside the app's project storage, writes to `<file>.part` and renames on success. A hidden render window (`?worker=render`, `render-worker.ts`, `render-preload.ts`) runs `renderMediaOnWeb()` on `ProjectComposition` in `export` mode (originals, not proxies) and streams chunks to main. The window is destroyed after every export.
- **Size:** 1080p or 720p means the short side, so portrait and square projects scale correctly (`exportSize` in `@studio/schema`, even sizes). The render uses the web renderer's `scale` option. Bitrate is 10 Mbit/s at 1080p and 5 Mbit/s at 720p (`export-settings.ts`).
- **Progress, estimate, cancel:** progress is encoded frames over total, sent at most four times a second; the estimate is elapsed time scaled by the fraction left, shown after 2%. Cancel aborts the render, deletes the partial file and destroys the window; a renderer that ignores the abort is destroyed after 10 seconds. A render window silent for 120 seconds fails the export.
- **History and logs:** `exports.json` holds finished, failed and cancelled exports (oldest first; version numbers are never reused). Each export writes `<project>/exports/<id>.log` (settings, destination, progress every 10%, the render window's warnings and errors, the outcome). Both are written by `@studio/project-store` (`exports.ts`).
- **Golden frames:** `e2e_m6.py` compares the preview with the export at five frames, scaled to 160x90, with a mean difference under 12 of 255. Measured: 4.6 to 5.7. The spike measured 40 dB PSNR for export against still.
- **Licence:** `renderMediaOnWeb` gets `licenseKey: "free-license"` (Remotion's Free License, chosen by the user on Nov 12). In 4.0.542 that only silences the warning: the library still tries a usage ping to `remotion.pro/api/track/register-usage-point` after every render. The CSP's `connect-src` blocks it, so nothing leaves the machine, and each export log shows two "violates the Content Security Policy" lines. They are expected.

## Verification (Nov 12)

M6 was written in a session that could not install dependencies, so it was first run here. It did not compile, and its e2e had bugs that hid results. Fixed:

- **Three type errors:** `nextExportVersion` was imported from `@studio/project-store` (it is in `@studio/schema`); `RenderJob.height` was a plain number, so the bitrate lookup did not compile (it is now `ExportHeight`, the size chosen in the dialog, not the output height); and the cast on the `renderMediaOnWeb` options broke inference of the composition's props. The cast is gone. The option names (`outputWritable`, `scale`, `onProgress({encodedFrames})`, `videoBitrate`, `signal`) were all right for 4.0.542, and `outputWritable` takes a `WritableStream<StreamTargetChunk>` as assumed.
- **Vite re-optimised mid-session.** The first export imported `@remotion/web-renderer`, which was not pre-bundled, so Vite optimised it at run time and reloaded every window, the editor included (the dialog lost its state). It also left "Mediabunny was loaded twice" in the render window. `@remotion/web-renderer` is now in `optimizeDeps.include` in `vite.renderer.config.ts`, and both are gone.
- **Golden frames failed by about 28 of 255, from the test, not the export.** Both frames were the same moment and layout, but the preview was uniformly less saturated: on macOS, page screenshots come out in the display's colour space (P3), while ffmpeg reads the export as sRGB. `e2e_m6.py` now starts Electron with `--force-color-profile=srgb` (through a new opt-in `electron_args` on `App` in `lib.py`, so other milestones' shots are unchanged).
- **The test's vlog had no dissolve.** Clips added at full length have no footage past the cut, so `setTransition` was refused without anyone noticing. It now trims both sides first, as M5 does. Cancel used to be pressed 30ms after the start, before the render began; it now waits for progress above 0%, so it stops a running render.
- **Added checks:** a full 1080p export (before, only 720p was ever finished), and a source file deleted mid-render (the export fails at the clip that uses it, keeps no file and records the failure in history and the log).

Result: `verify.py M6` passes 34 of 34 (`docs/reports/M6.md`). On the 24GB dev Mac with synthetic clips, a 16.7-second vlog exports in about 4 seconds at both 720p and 1080p, total memory peaks around 1.08GB, and the render window is gone afterwards (525MB total 30 seconds later). The Export button moved 13 visual shots, each only in the button's 163x28 box; those baselines and the new `dialog-export` were updated.

## Not built, and known limits

- **Gate 2 is not automated:** the 5-minute 1080p30 export, audio sync at the 5-minute mark and the 1.5GB peak. Run them by hand on the 8GB Mac with real footage. The automated sync check is weak: the test's music is 4 seconds long and the file pads it with silence, so "audio and video end together" proves little about sync.
- **A render failure is reported in technical terms.** A source file that vanishes mid-render shows "The export did not finish." followed by the raw `media://local/.../assets/<sha256>.mp4: 404 Not Found`, with no file name. Name the file (as the check before the start does) when error handling is reworked in M7.
- Leaving the project and coming back while an export runs loses the dialog's running state (the export carries on in main; a second start is refused with "An export is already running").
- Media proxy jobs are not paused during an export. If memory is tight on the 8GB Mac, pause the queue in `ExportService.start`.
- Disk-full and missing-disk handling beyond a readable error are M7.
